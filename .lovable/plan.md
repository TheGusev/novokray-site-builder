# Починить автозаполнение реквизитов по ИНН

## Что не так сейчас

Форма КП запрашивает данные напрямую из браузера и читает ключ из переменной `VITE_DADATA_TOKEN`. Такой переменной в проекте нет: ключ DaData сохранён под именем `DADATA_API_KEY` и доступен только на сервере. Поэтому код молча возвращает «ничего не найдено» — ещё до обращения к DaData. Плюс сборка на боевом сервере вообще не получает никаких `VITE_`-переменных, так что даже правильное имя не спасло бы.

Отдельно: класть ключ DaData в клиентский бандл нельзя — он был бы виден любому посетителю и его можно было бы «сжечь» по лимитам.

## Как исправим

1. **Серверный прокси.** В уже работающую службу приёма заявок (`server/lead-api.ts`, порт 8787) добавляем маршрут `POST /api/dadata`: принимает ИНН, сам ходит в DaData с ключом из серверного окружения, возвращает только нужные поля (название, полное название, ИНН, КПП, ОГРН, адрес, руководитель, статус). Ключ никогда не попадает в браузер.
2. **Клиент.** `lookupInnParty` начинает обращаться к `/api/dadata`. Различаем причины: «не найдено», «недействующая организация» (предупреждение, но поля заполняем), «сервис недоступен» — во всех случаях ручной ввод остаётся доступен, сообщение под полем становится понятным.
3. **Ключ на сервере.** `DADATA_API_KEY` добавляется в `/etc/dez-federation/lead.env` — тем же способом, что уже сделано для токена Telegram: если секрет задан в GitHub, деплой прописывает его автоматически, иначе выводит инструкцию.
4. **Nginx.** Документируем и проверяем блок `location = /api/dadata` рядом с существующим `location = /api/lead`, иначе запрос уйдёт в статику и вернёт 404/405.
5. **Проверка при деплое.** В workflow добавляется probe: локальный запрос к `127.0.0.1:8787/api/dadata` и внешний через домен, с понятной ошибкой, если nginx не настроен.
6. **Тесты.** Юнит-тесты на разбор ответа DaData (короткое/полное имя, отсутствие КПП у ИП, ликвидированная компания) и на валидацию ИНН (10/12 цифр, мусор).

## Технические детали

- `server/lead-api.ts`: новый обработчик, чтение `process.env.DADATA_API_KEY`, таймаут запроса ~5 с, ограничение частоты по IP, ответы вида `{ ok: true, party }` / `{ ok: false, reason }`.
- `src/lib/dadata.functions.ts`: убираем `import.meta.env.VITE_DADATA_TOKEN`, оставляем валидацию ИНН на клиенте, добавляем типизированный результат с причиной отказа.
- `src/routes/kp.tsx`: состояние `lookupState` расширяется под новые причины; поведение кнопки и ручного ввода не меняется.
- `deploy/lead.env.example`, `.github/workflows/deploy.yml`, `SERVER_DEPLOYMENT.md`: строка `DADATA_API_KEY=`, автоподстановка секрета, probe и таблица типовых ошибок.

## Что нужно от вас

Ключ DaData должен быть добавлен в секреты GitHub репозитория под именем `DADATA_API_KEY` (либо я дам одну команду для ручной вставки в `/etc/dez-federation/lead.env`). Без этого форма продолжит работать, но реквизиты придётся вводить руками.
