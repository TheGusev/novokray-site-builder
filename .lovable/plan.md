## План: автотесты валидации + аудит сайта на 100 баллов

### Часть 1. Автоматические тесты валидации каталога обработок

**Стек:** Vitest (уже доступен через `bunx vitest`), без UI-зависимостей — чистые unit-тесты на данные и функции из `src/data/treatmentCatalog.ts`.

**Создаём:**
- `src/data/__tests__/treatmentCatalog.test.ts` — основной файл тестов
- `vitest.config.ts` (если отсутствует) — минимальная конфигурация

**Группы тестов:**

1. **Целостность каталога**
   - У каждого `pest` есть `levels`, `works`, `meds`, корректные `barrierDays`.
   - Уникальность `id` у pests / works / levels.
   - У каждой работы валидный `unit` из разрешённого набора.

2. **Степень заражения ↔ работы (`levelLock`)**
   - Для каждой работы с `levelLock` проверить, что список уровней — подмножество допустимых.
   - Snapshot-таблица: при level=1 показываются только работы без lock или с lock содержащим 1; аналогично для 2-3 и 4-5.
   - Множитель цены: 1 → ×1, 2 → ×1.5, 3 → ×2 (через хелпер `getLevelMultiplier`).
   - Срок гарантии по уровню: 1 → 90, 2 → 60, 3 → 30.

3. **Единицы измерения ↔ количество (`clampQty` / `getElementLimits`)**
   - Для каждого unit (`шт`, `м.п.`, `м²`, `сотка`, `точка`, `комплект`) — min/max/step из `UNIT_LIMITS` применяются.
   - `clampQty(-5, unit)` → min; `clampQty(99999, unit)` → max; дробные значения округляются по `step`.
   - Element-специфичные `min/max/step` переопределяют дефолтные `UNIT_LIMITS`.

4. **Уличные правила (клещи/комары/мошка/мухи)**
   - У всех outdoor-pests флаг `outdoor: true`.
   - Для клещей единица «сотка» доступна; для комаров — «точка»/«м²».
   - Препараты outdoor содержат как минимум Медилис-Ципер / Сипаз-Супер.
   - `barrierDays` для клещей ≥ 21, для комаров ≥ 30.

5. **Расчёт стоимости блока**
   - Сумма позиций × коэффициент уровня + барьер = ожидаемая сумма (фикстура из 2-3 кейсов).
   - Пустой блок (qty=0 у всех работ) → ошибка валидации.

**Скрипт запуска:** добавить `"test": "vitest run"` в `package.json` если нет; запускать `bunx vitest run`.

### Технические заметки
- Тесты — pure functions, без сети/DOM, время выполнения <1с.
- Аудит выполняется батчами параллельных правок по группам файлов (route-группы), чтобы не плодить мелкие коммиты.
- `routeTree.gen.ts` не редактирую — только route-файлы.
- Sitemap пересобирается строго из реальных роутов + данных (`src/data/blog.ts`, `services.ts`, `cities.ts`, `districts.ts`, `docs.ts`).

### Что НЕ делаю без отдельного запроса
- Не меняю дизайн-токены и визуальную айдентику.
- Не добавляю новые роуты/разделы.
- Не подключаю Lovable Cloud / БД (всё уже файловое).
- Не трогаю бизнес-логику расчётов договора, кроме того, что покрываю тестами уже существующее поведение.
